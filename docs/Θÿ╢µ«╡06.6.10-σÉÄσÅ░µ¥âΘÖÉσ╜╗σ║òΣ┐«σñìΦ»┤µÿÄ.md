# 阶段 06.6.10：后台权限彻底修复说明

## 这次修复针对的实际问题

原项目出现过：

- `/admin` 可以进入，但左侧后台菜单为空；
- `/admin/products` 显示 403，没有进入“9 大 AI 产品”的权限；
- 浏览器可能继续携带旧版本 `admin_session`，而当前代码使用了不同的 `ADMIN_SESSION_SECRET` 或会话规则；
- Proxy 以前只检查 cookie 是否存在，不验证 cookie 签名，因此“过期/失效 cookie”会被允许进入 `/admin` 页面，随后 `/api/admin/me` 验证失败，前端误显示为“没有权限”。

## 彻底修复方案

### 1. 管理后台会话升级为 v2

新的 cookie：

```text
admin_session_v2
```

登录时会自动清除旧的：

```text
admin_session
```

这样旧项目、旧密钥、旧会话不会继续污染当前后台权限判断。

### 2. Next.js 16 Proxy 开始验证 session 签名

以前只是：

```text
cookie 存在 -> 放行 /admin
```

现在变成：

```text
cookie 存在
-> 校验签名
-> 校验过期时间
-> 无效则清除 cookie 并回到登录页
```

因此不会再出现“看似登录了，但内部权限接口认为未登录”的假 403。

### 3. admin 账号采用数据库兼容超级管理员规则

满足以下任一条件即可作为超级管理员：

- 管理员用户名是 `admin`；
- 数据库中只有一个 ACTIVE 管理员；
- 管理员的旧 `role` 字段为 `SUPER_ADMIN / SUPERADMIN`；
- 通过 RBAC 关联到“超级管理员”角色。

所以历史数据库即使 `admin_roles / role_permissions` 数据不完整，唯一的 `admin` 仍然可以使用全部 CMS 功能。

### 4. 登录时自动修复 RBAC 关系

登录成功以后，系统会尝试把当前 `admin` 绑定到“超级管理员”角色。

即使角色表暂时不可用，也不会阻断登录，因为真正的超级管理员判定不再依赖该关联表。

### 5. 前端不再把 /api/admin/me 的临时异常误报成 403

只要 Proxy 已经验证当前 session 有效，后台菜单不会再因为权限接口瞬时异常而整体变空。

真正的数据新增、修改、删除仍由后端 `requirePermission()` 校验，所以只是修复错误的 UI 权限状态，不会绕过服务端权限。

## 首次使用

升级后建议直接重新登录一次。

如果数据库中的 RBAC 数据也需要重新整理，可执行：

```bash
npm run admin:repair
```

也可以继续使用：

```bash
npm run seed:rbac
```
